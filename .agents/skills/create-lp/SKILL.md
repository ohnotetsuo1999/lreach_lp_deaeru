# LP作成

LP専用リポジトリのルートで実行する。デザインはこのリポジトリ、回答保存・通知・番号台帳はLreach backendが担当する。利用者にDBやJSONの編集を求めず、選択内容を実行用JSONへ変換する。

スキル自体の更新・相談を依頼された場合は、その依頼だけを行い、LP作成の質問や採番・デプロイを始めない。

## 選択肢UIの使い方

- 最初からLP名・媒体・デザイン等の自由記述をまとめて求めない。未回答の項目を **採番方法 → 広告タグ（GTM）→ LINEシナリオ → デザインの進め方** の順に1問ずつ提示する。回答を受け取ってから次へ進む。指定済みの項目は聞き直さない。
- Codexでは `request_user_input_async` の `questions` に1問だけ入れ、`title` と `options` でクリックできる選択肢を出す。Claude等では利用可能な選択式質問ツールを使う。`request_user_input` はその環境の利用条件を満たす場合だけ使う。ツールの利用条件がこの手順より優先する。
- 選択式質問ツールが使える間は、チャット本文の箇条書きや番号入力で代用しない。使えない場合だけ、その旨を短く伝えて同じ候補を番号付きで提示する。ツールを使うためだけに動作モードを変更しない。
- 先頭の選択肢が表示上選ばれていても、利用者の回答には数えない。回答待ちの時間経過を同意とみなさず、未回答の設定を勝手に決めない。非同期の質問後は独立した読み取り作業のみ進め、回答に依存する処理は待つ。
- 選択肢がツールの上限を超える場合は、広告主等で絞り込むか、ページを分けて全候補へ到達できるようにする。候補を黙って省略しない。複数選択に非対応なら1つ選んだ後に追加の要否を選んでもらう。

最初の質問例（未指定の場合）：
```json
{"questions":[{"title":"LP番号の決め方を選んでください。","options":["自動で採番","LP番号を指定"]}]}
```

## 必要な初期設定

- Node.js、npm依存、GitHubの書き込み権限、Vercel CLIへのログインとLP専用プロジェクトへのアクセス権。端末のlinkはCLIが自動作成する。
- 通常はURL・トークンの入力不要。CLIが本番backendへ自動接続し、LPプロジェクトのVercel Development設定から限定した発行用トークンだけを取得する。秘密の値をチャット・Git・HTML・端末ファイルに出さない。
- 手動の別環境接続は `LP_PUBLISH_API_URL` と `LP_PUBLISH_TOKEN` を両方指定する。認証失敗時はまずVercelログイン・LPプロジェクト権限を確認し、利用者へ秘密の値を質問しない。
- backendのDB migration、既存番号の棚卸し、広告主確認済みタグの登録。未設定のAPIや未完了の台帳をローカル採番で代用しない。
- mainのみで運用する。自動発行はPreviewまで。VercelのGit自動連携があるとmain pushで本番公開されうるため、このPreview用CLIはGit自動連携のないプロジェクトで使う。

## 1. 採番方法を選ぶ

まず「自動で採番／LP番号を指定」の選択肢UIを出す。この質問はAPIが未設定でも提示できる。

- 自動は `code:null` を保存する。この時点では番号を予約しない。発行時にbackendの `reserve_lp_publication_v2` がLPマスターと既存の制作・流入・回答台帳を参照し、未使用の続番を同一トランザクションで予約する。採番順は `A〜Z → AA〜ZZ → 次の数値のA`。最大が `LP99ZZ` なら次は `LP100A`、その次は `LP100B`。`LP100Z → LP100AA`、`LP100ZZ → LP101A` と続く。発行APIが `numbering.policy=suffix-v1` を返すことを確認し、旧方式のままなら採番前に停止する。大文字は表示名、保存・URLは小文字。最新番号をローカルの固定値や文字列順だけで決めず、予約時のDBを正とする。
- 同時発行はDBの採番ロックと一意制約で重複を防ぐ。同じ依頼IDの再実行は元の番号を返す。既存の空き番号の穴埋めや、エラー時の別依頼IDでの取り直しはしない。
- 指定を選んだ場合だけ、LP番号を1つ入力してもらう。例は `LP99Y`、`99A`、`08A`、`01A`。これらは入力形式の例で、空き番号の候補ではない。CLIは `100A`・`LP100A` 等を `lp100a` に正規化する。
- 既存番号の棚卸しやAPIで重複が判明したら「別のLP番号を指定／自動で採番」の選択肢に戻す。既存LPを上書きせず、勝手に別番号へ変更しない。

## 2. 広告タグ（GTM）を選ぶ

`npm run lp-saiban -- options` で登録済みのタグ・LINEシナリオ・元の挙動を取得する。スキル名は `create-lp`、内部の共通CLI名は引き続き `lp-saiban` を使う。

- APIの `tags` からGTM（`provider: "gtm"`）を選択肢UIに表示する。候補のラベルには取得できた広告主名、タグ名、種類、識別子（`GTM-...`）を含め、同名でも区別できるようにする。広告主が不明で選択を特定できなければ追加確認する。
- 「広告タグなし」も選択可能にする。選択されたタグのDBの `id` だけを `tagIds` に保存し、なしは `[]` にする。表示用のGTM識別子とDBのIDを取り違えない。
- GTM以外の登録済みタグを使う希望がある場合は、APIのMeta・TikTok・Google Ads等の候補から同様に選んでもらう。複数タグが必要なら追加選択し、同じIDを重複させない。
- タグや広告主、IDを推測・固定しない。GTM管理画面のコンテナ編集や公開は、この登録済みタグの選択には含めない。
- API未設定・停止時は「設定を復旧して選ぶ／タグ・シナリオを保留してデザインへ進む」をUIで提示する。後者でも保留を「タグなし」「自動配信なし」に変換しない。デザインだけ進め、復旧後に未回答のタグ・シナリオへ戻る。必須設定が確定するまで `issue` を実行しない。

## 3. LINE追加後のシナリオを選ぶ

APIの `lineScenarios` に存在する候補だけを、次の表示名と説明を使って選択肢UIに出す。選んだAPIの `key` を `lineScenarioKey` に保存する。

| key | 表示名 | 説明 |
| --- | --- | --- |
| `lp99y` | 案内方法を選択（99Yと同じ） | LINE追加後に案内方法を選べる |
| `legacy_b` | 従来の予約案内 | 従来の予約案内へ進む |
| `none` | 自動配信なし（手動チャット） | 初回シナリオを送らず手動で対応する |

自動配信なしは既存予約の通知等を全て無効化する設定ではない。新規LPの回答・LINE遷移は99Y互換で、08A等の別基盤のシナリオは候補にしない。候補が空なら設定不足として保留し、CLIの既定値で回答を代用しない。

## 4. デザインの進め方を選ぶ

前の3項目の回答後（または設定不足による保留を選んだ場合）に、次の3択をUIで提示する。

1. 希望するデザインを添付する
2. HTMLファイルを送る
3. このチャットの会話で一緒に作っていく

これは進め方の選択だけに使う。添付・HTMLを選んだ後は、通常のチャットでファイルの添付を案内して待つ。テキスト専用の質問ツール内でファイル送信を求めない。既に添付があれば使い、再送を求めない。

- デザイン添付：画像・PDF等を読み、HTMLにする。Figmaは利用可能な連携からHTML化し、利用不可なら画像またはHTMLを案内する。
- HTML：ファイルを確認して `designFile` に指定する。フォーム位置等を必要に応じて整える。
- チャットで共同作成：目的・見せたい内容を短く聞き、案を作って会話で編集する。テンプレートを使う場合だけ `npm run lp-saiban -- templates` の「シンプル／特徴カード」を追加で選んでもらう。テンプレート選択で共同作成を終わらせない。

この段階で、未指定のLP名、掲載文章・画像を必要な分だけ確認する。媒体は利用者が指定した場合だけ登録する。URL末尾は既存LPと同じ動的な `[id]` であり、LP発行時の設定項目ではない。流入IDを質問したり、`direct` 等を発行仕様の固定値・既定値として保存したりしない。`/deaeru/<採番コード>/[id]/` の各アクセスで受け取ったIDを回答のLPキーと流入URLに反映する。現在の受付APIが扱うIDは英小文字・数字・ハイフン（例：`001`、`meta`、`campaign-1`）。表示確認URLの `001` は動作確認用の一例であり、許可するIDを固定するものではない。技術用のslug等は会話から作成する。

## 5. 作成・表示確認

確定した回答を `.lp-publish/draft-<slug>.json` に保存する。例：
```json
{"slug":"spring-career","title":"あなたらしい働き方を、一緒に。","template":"career-cards","content":{"brand":"キャリア相談","lead":"希望の働き方をお聞かせください。"},"code":null,"media":"Meta","mediaType":"インハウス","note":"99Y互換","tagIds":[],"lineScenarioKey":"lp99y"}
```
この例の値は回答の既定値ではない。手動採番は `code:"lp100a"`、添付HTMLは `designFile` を指定する。タグ・シナリオが保留なら未確定と明示してデザインHTMLだけ作り、実行用仕様への変換と `init` は確定後に行う。

`npm run lp-saiban -- init .lp-publish/draft-<slug>.json` を実行し、生成した `designs/<slug>.html` を希望に合わせて編集する。フォーム位置は `{{LREACH_FORM}}` を1つ、画像は `public/issued-assets/<slug>/` に置く。保存処理・通知先・広告タグをデザインに直接追加しない。

誇大な実績・架空の口コミを足さない。添付HTMLに既存のタグや送信処理がある場合も検査し、選択したタグの二重実行や未承認の送信を防ぐ。フォーム入りの完成HTMLを `renderPublishedPage` でローカル描画し、PC・スマホの見出し・表示・フォーム位置を確認する。秘密情報や承認されていない送信先がないことを確かめる。

## 6. Vercelへデプロイ

デザインと選択内容が確定したら、LP番号の指定内容（自動なら「自動採番」）、GTMタグ、LINEシナリオと確認できるデザインを示す。

- 発行・デプロイまで既に依頼されていれば、その範囲で進める。毎回承認を取り直さない。
- デプロイが未依頼なら、完成物を確認できる状態にして、通常のチャットで「この内容でVercel Previewへデプロイしてよいですか」と確認する。許可されていない質問ツールを承認に使わない。スキルの呼び出しだけを外部発行の許可とは扱わない。

`npm run lp-saiban -- issue specs/<slug>.json` で、番号予約・タグ取得・ルート生成・ビルド・対象ファイルだけのコミット・main push・Vercel Preview・台帳へのURL登録を順に実行する。別の変更やステージ済みファイルがあれば巻き込まず停止理由を解消する。強制pushしない。

出力URLをブラウザで確認し、LP番号・確認URL・選択したタグとLINEシナリオ・検証済み範囲・未確認事項を返す。テスト回答は許可された接続先と対象だけで行い、READYだけで回答保存・Slack・LINEも動いたとは報告しない。

## 再開と境界

- 同じ仕様と `.lp-publish/<slug>.json` を保持して同じ `issue` を再実行する。登録失敗なら既存URLの登録だけ再開し、新しい番号やデプロイを作らない。
- デプロイ結果が不明なときはVercelの実結果を確認する。番号の取り直し、状態削除、闇雲な再デプロイをしない。
- 予約後にデザインを修正した場合は、未デプロイであることを確認して `node scripts/lp/publish.mjs prepare specs/<slug>.json` で同じ番号のコードを再生成する。デプロイ後の改修は新規発行とは分けて扱う。
- 既存Lreach本体のdevelop/mainへのマージ、Production昇格、既存URL・HTTPSの切替はこのコマンドに含めない。広告計測はProductionの明示有効化時だけ動く。

## 仕組みの説明

発行・回答保存・通知・デプロイの構成と確認範囲は、リポジトリルートの `docs/lp-publication-flow.md` を参照する。options APIはLPマスター・タグ・シナリオを返すもので、既存LPのデザインHTMLや画像を取得するものではない。既存LPを参照する場合はリポジトリのページ・画像を確認する。共通フォームは99Y互換の5項目であり、旧LP固有の全質問・通知・計測の完全複製とは説明しない。

Previewの表示確認と回答受付を区別する。接続先backendがproduction運用の場合、published状態と登録済みProduction URLが必要で、Preview登録だけでは回答保存できない。本番受付ではLP側の `LREACH_DEPLOY_ENV=production`・`OUTBOUND_DELIVERY_ENABLED=true`・`OUTBOUND_DISABLED=false` もProduction環境に明示登録してデプロイする。未設定だと送信ガードがbackendへのPOSTを止める。Previewへ本番送信設定を適用しない。Slackは専用の有効化設定・宛先・トークンが必要。受付や通知がOFFなら、旧LPと同じく動くと説明せず、実際の設定と未検証範囲を伝える。

## 完了判定

回答受付の完成を依頼された場合は、許可された環境でテストと明記した回答をフォームから送信し、受付IDに対応する `lp_sessions`・`users_info`、プロトタイプのLP Sessions画面、旧LPと同じSlack通知先を照合する。HTTP成功・同一DB・設定ONだけで完成扱いにしない。同じ受付IDでの再送でも保存と通知が増えないことを確認する。確認日時・LP番号・流入ID・受付ID・画面と通知の証跡を残す。
